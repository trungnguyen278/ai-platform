# Development log — November 2026

## 2026-11-01 — The app API, version 1.0

**Done:** [`protocols/app/`](../../protocols/app/README.md): how ai-app talks to ai-cloud, with its schema and three examples. Version 1.0 carries ADR-0008's sign-in and the account.
- **Signing in:**
  - a nonce from the cloud;
  - the provider's ID token, carrying that nonce;
  - the token exchange at `/app/token` (RFC 8693).
- **Sessions:**
  - refreshing, with refresh tokens rotated;
  - one presented twice ends its session;
  - signing out at `/app/revoke` (RFC 7009).
- **The account:** reading and changing it, with an ETag, and deleting it; linking and removing identities; listing and ending sessions.
- **Apple:** its authorization code comes with its ID token. The cloud exchanges it for Apple's refresh token, kept encrypted, so that it can revoke it as Apple asks when the identity goes or the account is deleted.
- **Deleting the account** needs a fresh sign-in first, so that a phone left unlocked cannot do it.
- **Errors:** OAuth's at the OAuth endpoints, and Problem Details elsewhere, with a `type` of its own for each error the app acts on.
- **Development:** an endpoint of the development environment makes ID tokens for test people. Sign-in then runs the same path with neither Google nor Apple.

The examples carry ID tokens whose claims read as a provider's, signed by nobody. `tools/check.py` checks them against the schema. Four broken examples, tried by hand, failed it.

**Problems / unfinished:** Neither the app nor the cloud implements it yet. Homes, their members and devices, and set-up's registration come in later minor versions.

**Next:** The cloud's side, in ai-cloud's `accounts` module. The app's `account` module, against the development environment first.

## 2026-11-04 — The app API 1.3: refreshing again after a lost answer

**Done:** [ADR-0011](../decisions/0011-refreshing-again.md), and the app API 1.3, which specifies it.
- **The problem,** met while building ai-app's client: a refresh whose answer is lost on the way ends the session. The cloud has rotated the token, and the app's next refresh presents the old one, which counts as stolen.
- **The rule:** for `refresh_reuse`, 60 seconds, after its first use, a refresh token refreshes again while its replacement is unused, and the replacement then stops working. Any other token presented again still ends its session. Okta and Auth0 allow the same retry.
- **`sign-in.json`** now shows the retry. Its stolen copy comes after the app has refreshed again, so that the example replays without waiting for the window to pass.

**Decisions:** delegated to the assistant, as in the entry before. Okta's longest grace period sets the starting point; ai-cloud's configuration sets its own.

**Problems / unfinished:** No side implements 1.3 yet.

**Next:** After the merge, tag `app/v1.3`. Then ai-cloud implements it, without a new table: a token may refresh again if it is the session's last used one. Then ai-app's `account`, whose session retries a refresh only after no answer came.

## 2026-11-05 — Registering a device into a home: ADR-0012 and the app API 1.4

**Done:** [ADR-0012](../decisions/0012-registering-devices.md), and the app API 1.4, which specifies it, with a new example, `devices.json`.
- **The flow:** the owner or an admin gets a challenge for a home, the device signs its registration with it over set-up, and the app relays it. The cloud answers with the device, and the app sends `finish`, then waits for the device's first connection.
- **The challenge:** 32 random bytes, for one home and one account, valid 300 s, and used by the first registration that presents it. It names `server`, the address that devices use.
- **The answers:** `201`, a new device; `200`, the same device, already in the home; `400` `registration_invalid`; `409` `device_taken`, for a device in another home, or a key or an identifier that is another device's; `409` `device_limit_reached`. A retry with the same `Idempotency-Key` gets the first answer.
- **The trust:** the owner's session, which the code on the device's screen secures, and the device's signature over the challenge. No attestation.
- **Also:** reading a home's devices, and removing one, which revokes it as deleting its home does.
- **Compared:** ESP RainMaker's challenge-response mapping, the closest; AWS IoT's provisioning by trusted user; Tuya's pairing token; Matter's commissioning; WebAuthn's registration; Azure's TPM attestation; Amazon's Frustration-Free Setup; Google Home's and Apple Home's help.
- **Set-up stays 2.0,** with no message changed: its README says where the challenge and the address come from. The cloud link does not change.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03 for long-term development: all of ADR-0012. Among them: the cloud names the devices' address with each challenge; the binding holds once the cloud accepts the registration, not after a first connection; no attestation; one code for any failed registration.

**Review:**
- **A device read as a member:** `from_cloud` read any body with a `kind` as a member, and a device has one. The member's rule now leaves out bodies with `connected`.
- **A limit that blocked a device's return:** the first draft refused a challenge in a full home, so a device that had lost its state could not come back. The limit now counts new devices only.
- **A key with another identifier:** the first draft refused an identifier held with another key, but not the reverse. Both are `device_taken` now, and identifiers compare as UUIDs, in any case (RFC 9562, §4).
- **Planted bodies:** 96 checks of good and broken bodies, against each definition and through the dispatch, with `$` read as ECMA-262 reads it. The example's story holds: each registration verifies with the key in its header, and names the challenge and server just given.
- **Mutants:** 37, of the schema and of the example, all killed.
- The review checklist gains dispatch, limits and retries, and matching.

**Problems / unfinished:**
- No side implements 1.4 yet.
- **Two choices for the owner,** which people will see:
  - a device's name in a home: Apple Home asks for one as it adds an accessory;
  - what a device keeps once revoked (PROV-4): Tuya's unbinding clears its pairing and schedule data, and Google Home's removal resets the device's settings. ai-robot decides it for the robot.
- **`tools/check.py` reads a pattern's `$` as Python does,** which also matches before a last newline: an example whose value ends with one would pass CI, though every side refuses it (ADR-0010).

**Next:** After the merge, tag `app/v1.4`. Then ai-cloud's `devices`: the registry, the endpoints, the token endpoint against the registry, and revoking a deleted home's devices. Then ai-app's `setup` and `devices`.

## 2026-11-05 — The check reads a pattern's end as ECMA-262 does

**Done:** `tools/check.py` reads a pattern's final `$` as the very end, the gap the entry before names. JSON Schema's patterns are ECMA-262's, whose `$` matches only at the end (ECMA-262, §22.2.2.4). Python's also matches before a last newline, so an example value ending in one passed CI, though every side refuses it.
- **How:** the examples and the catalogs are validated against a copy of their schema whose final `$`s are Python's `\Z`, written by ai-cloud's and ai-robot's own `ecma_end`.
- **The proof:** the check plants eight values it must accept or refuse, as it plants patterns for ADR-0010, and a catalog ID ending in a newline. A time zone ending in a newline, in an example of each protocol, and a catalog ID ending in one, fail the new check and passed the old. The 15 mutants of the reading are all killed.

**Decisions:** delegated to the assistant, as on 2026-11-03.
- **A copy of the schema, rather than an override of `pattern`,** which ai-cloud and ai-robot use. jsonschema 4.26 reads a schema's regular expressions with Python's `re` in four places: `pattern`, `patternProperties`, and the lookups of `additionalProperties` and `unevaluatedProperties`, the second following `$ref`s through the schema it was given. It takes no other engine: [python-jsonschema#1142](https://github.com/python-jsonschema/jsonschema/issues/1142) is open, and [#1561](https://github.com/python-jsonschema/jsonschema/pull/1561), which would let one replace `re` in those four places, is not merged. An override reaches `pattern` alone; the copy reaches all four. The sides need only `pattern`, as no protocol uses `patternProperties`.
- **A problem quotes the pattern as the check read it,** ending in `\Z`, which shows why a value ending in a newline fails.
- Sources, read 2026-11-05: JSON Schema validation 2020-12, §6.3.3, and core 2020-12, §10.3.2.2; ECMA-262 (the 2027 draft), §22.2.2.4; Python's `re`, 3.13, where `\Z` matches only at the end; the JSON Schema Test Suite's `optional/ecmascript-regex.json`, which has the same case.

**Problems / unfinished:** If a protocol comes to use `patternProperties`, ai-cloud's and ai-robot's validators need the same reading of its keys.

**Next:** unchanged: ai-cloud's `devices`, then ai-app's `setup` and `devices`.

## 2026-11-12 — Setting a device up: ADR-0013 and the app API 1.5

No room, no "found nearby" pop-up, and a new network never registers the device again.
- **The app API 1.5:** a device has a `name` in its home, which the app sends with the registration, and an `etag`. The owner and admins rename it with `PATCH` and `If-Match`. A device that registers again keeps its name. A new example shows the rename, a member refused it, and the name kept.
- **`Idempotency-Key`:** the README says that a key's uniqueness is its kind of request's, as the IETF's draft 08 leaves it to the server (§2.2), and as ai-cloud does: each of its modules keeps its own keys, by account, and compares the method, the path and the body.
- **Set-up stays 2.0:** its README now says how the app runs it: a typed code, the network skipped, a bound device's session, what the person meets, and what follows an interruption. A new example, `wifi-change.json`, gives a bound robot another network.

**Decisions:** the flow and its four choices are the owner's. The rest is delegated to the assistant, as the owner chose on 2026-11-03:
- **the name travels with the registration,** so that a set-up interrupted after it leaves a named device, and keeping it sends nothing;
- **a home's name's rules, and duplicates allowed,** as for homes and people. HomeKit refuses a name that another object of the home has, and its guidelines shape names for Siri: no device here is called by its name, and two robots of one model give the same one;
- **the `etag` changes with the name only,** so that the device's connections never race a rename;
- **a bound device's session is set-up 2.0 as written,** so no version: it refuses `register` and serves the rest, and whoever reads the code stands at the device, whose screen changes the same settings;
- **a typed code with several devices in set-up** asks for the discriminator too, as Matter's manual code carries part of its own, rather than spend an attempt on each device.

**Review:**
- **Dispatch:** a device's new name has a home's new name's shape, so `from_app` reads both as `home_update`, whose `name` is the same; its description says so, as it already did for a profile's name. A registration's `name` sets off `home_update` too, with the same rule.
- **Planted bodies:** 39, through the dispatch and against each new definition. **Mutants:** 13, of the schema and the examples, all killed.
- The review checklist gains bodies of one shape, fields kept optional for the previous tag, and walking interruptions.

**Problems / unfinished:**
- **`If-Match` with weak ETags:** the app API's `etag`s are weak (`W/"2"`) since 1.1, and RFC 9110 says that `If-Match` compares strongly (§13.1.1), which a weak tag never passes (§8.8.3.2). ai-cloud compares them as written. Who changes what, the ETags or the text, is a task of its own.

## 2026-11-12 — JSON that every side can hold: ADR-0014 and the cloud link 3.1

**Done:** the clarifications that ai-cloud's first sessions asked for (ai-cloud#26, #27), as the cloud link 3.1, and [ADR-0014](../decisions/0014-json-every-side-can-hold.md), which set-up 2.1 and the app API 1.6 adopt next.
- **ADR-0014:** every JSON text a protocol carries is I-JSON (RFC 7493), holds no U+0000, and nests at most 64 deep. A receiver must refuse a lone surrogate, a U+0000 or deeper nesting, may refuse the rest of I-JSON's limits, and refuses such a text as one that it cannot read, however far its reader got: the answer depends on the text, not on where a parser gives up.
- **What a side cannot answer** (raised in the coordinator's review): a message that it can answer, a JSON object that every side holds with a `type` and, but in the five unnumbered types, a `seq`, gets an `error` with `reply_to`, and the session goes on. Any other frame ends the session with `bye` `invalid_message`: binary, not JSON or not JSON that every side holds, not an object, no string `type`, a numbered type without a `seq`, or a `hello`, `ping`, `pong` or `reconnect` that fails. A 3.0 side takes the new reason as `error`.
- **A message over 1 MiB:** the receiver's WebSocket closes with 1009, as uvicorn 0.54 (websockets 17.3's `PayloadTooBig`, the default `websockets-sansio`) and aiohttp 3.14 (`max_msg_size`) both do, so no side can answer `invalid_message` as 3.0 said. Both sides end the session, which no `bye` can say: resumed, it would carry the same message again.
- **The token endpoint's refusals:** `invalid_client` (401) only for a key the cloud does not know or has revoked; `invalid_grant` (400) for an assertion of a known key that fails; `invalid_request` (400) for a malformed request; `temporarily_unavailable` (429) with `Retry-After`. A device offers set-up after the first only.
- **A 429 at the upgrade:** the text already sent the device to its backoff for any status but 401 and 403; the row now names 429 and `Retry-After` as a date too.
- **`"type": "object"`** on each object definition of `schema.json`, which Ajv's `strictTypes` asks for. A differential check over the examples, each value swapped for 12 kinds of value, gave the same 33,600 judgements before and after.
- **`tools/check.py`** holds every example to ADR-0014, with planted texts for each limit; a new example, `errors.json`, shows a message that fails answered with `error`, and a U+0000 ending the session with `bye`.

**Decisions,** all delegated to the assistant:
- **`invalid_grant` for a failing assertion of a known key,** although RFC 7523 §3.2 names `invalid_client` for a client assertion: the device's assertion is its grant too (RFC 6749 §1.3.4), RFC 7523 §3.1 answers a failing grant with `invalid_grant`, and the device must tell "set me up again" from "try again". ai-robot already does: only `invalid_client` sends it to set-up.
- **No U+0000 anywhere,** as PostgreSQL 18 stores none in `text` and refuses `\u0000` in `jsonb`; RFC 8264 §9.12 keeps controls out of identifiers.
- **64 levels,** .NET's default `MaxDepth` and ai-cloud's `max_json_depth`; RFC 8259 §9 lets a parser limit depth. The examples nest at most 9 deep.
- **A frame that cannot be answered ends the session,** with a new `bye` reason rather than `error` without `reply_to`, which the schema refuses: ignored, a lost number ends the session later as `out_of_sequence`; counted, it can drop the next message as a duplicate. HTTP/2 splits errors the same way, by whether they can be tied to a stream (RFC 9113 §5.4); MQTT 5 ends a connection on "Malformed Packet" (§2.4) and on a packet too large (§3.1.2.11.4), and Discord's gateway closes with "Decode error".
- **ADR-0014's refusal is the unanswerable frame's,** whatever the reader saw, so that every reader answers the same text alike: ai-cloud's `read_json` gives up on depth and lone surrogates before any `type` is known.

**Review:** 16 mutants, of the schema, the examples and the check; 15 killed. The survivor, `is_error` typed as a string, shows that nothing tests the dispatch's typing: set-up 2.1 adds a check that each object definition says so, once set-up's schema does. The checklist gains ADR-0014, `type: object`, and what a side does with a frame that it cannot answer.

**Next:** after the merge, tag `cloud/v3.1`. ai-cloud: `invalid_grant` for an assertion that fails; refusing U+0000; `bye` `invalid_message` for every frame that it cannot answer, where today it ignores what it cannot read or number and logs it, sends `no_hello` for an unreadable `hello`, and `error` for an unreadable `ping`; and ending the session on a 1009. ai-robot: the same `bye` and ADR-0014's refusals; ending the session on a 1009, where today it counts the oversized message as the next number and answers it; and `Retry-After` from the token endpoint.

## 2026-11-12 — Set-up 2.1: what 2.0 left open

**Done:** set-up 2.1, which adopts ADR-0014 and answers what the review of ai-app's client asked (ai-app#23). What it makes plain applies to 2.0 sides too:
- **Fragments:** a message has 1 to 8192 bytes; a fragment may carry none of them, and adds nothing; a receiver holds the announced length at most, however many fragments come; and the text lists each fragment that does not fit, which ends the session without a message. An idle session counts whole messages only.
- **`reply_to`** on every error whose answered `seq` can be read, in the exchange too: `version` answers the app's `hello` (1), `code` its `confirm` (3).
- **A message that cannot be read** gets the error `protocol` without `reply_to`, and the session ends: one that is not JSON, not an object or without a `seq`, or JSON that a side cannot hold, however far its reader got, as ADR-0014 now says for every protocol. The robot already ends the session on every such `protocol`.
- **`busy`** answers a second app's `hello` once its last fragment has come, with `seq` 1 and `reply_to` 1, to that app only; the device then ends that connection, and the session that runs goes on. An app that connects once set-up has closed gets no message, and meets an interruption.
- **`"type": "object"`** on the schema's object definitions, as for the cloud link; the same 4,968 judgements before and after. `tools/check.py` now asks every schema for the types that Ajv's strictTypes asks for, as ai-app compiles them, and the catalogs' schema already gave them.
- **A new example,** `errors.json`: `busy`, `version` and `code`, each with its `reply_to`.
- The status line: the robot implements 2.0, the app its client (ai-app#23), the cloud the registration through the app API 1.4 (ai-cloud#25).

**Decisions,** all delegated to the assistant:
- **`busy` answers the `hello`,** as Matter's CASE server answers the handshake's first message with a busy status report, rather than the first write: the app then reads an answer to what it sent.
- **To that app only:** the device indicates each message to the app it answers. On the robot, BlueZ indicates a changed `Value` to every subscribed device, so that the first app also received the second's `busy`; `AcquireNotify` gives one device its own channel since BlueZ 5.80 (Ubuntu 26.04, the robot's, has 5.85); before it, 5.69 to 5.79 included, an acquired channel still reached every subscribed device (`sock_io_read` in `src/gatt-database.c` at each release tag, checked against BlueZ's source by the coordinator, 2026-11-12).
- **Nothing to an app once set-up has closed:** `busy` would send the person to wait, where the device needs opening again, which the interruption's row says.
- **A minor version,** although nothing on the wire changes but ADR-0014's refusals, so that a side can say which text it follows; as the app API 1.2 did with patterns.

**Review:** 13 mutants of the check, the schema and the example, all killed, and the cloud link's 16 again, all killed: the object-type check kills the survivor of 3.1's review. The checklist gains a type for every typed keyword, `reply_to` whenever the `seq` can be read, to whom a message goes, and every way a framing can fail.

**Next:** after the merge, tag `setup/v2.1`. ai-robot: `reply_to` on the exchange's errors, `busy` after the `hello` and to its app only, nothing once set-up has closed, empty fragments held as nothing, and ADR-0014's refusals, without `reply_to`. ai-app: ADR-0014's refusals, ending the session after each, `busy` read with `reply_to`, and `strictTypes` on for set-up's schema.
