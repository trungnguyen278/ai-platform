# Development log — November 2026

## 2026-11-01 — The app API, version 1.0

**Done:** [`protocols/app/`](../../protocols/app/README.md): how ai-app talks to ai-cloud, with its schema and three examples. Version 1.0 carries ADR-0008's sign-in and the account.
- **Signing in:**
  - a nonce from the cloud;
  - the provider's ID token, carrying that nonce;
  - the token exchange at `/app/token` (RFC 8693).
- **Sessions:**
  - refreshing, with refresh tokens rotated;
  - one presented twice ends its session;
  - signing out at `/app/revoke` (RFC 7009).
- **The account:** reading and changing it, with an ETag, and deleting it; linking and removing identities; listing and ending sessions.
- **Apple:** its authorization code comes with its ID token. The cloud exchanges it for Apple's refresh token, kept encrypted, so that it can revoke it as Apple asks when the identity goes or the account is deleted.
- **Deleting the account** needs a fresh sign-in first, so that a phone left unlocked cannot do it.
- **Errors:** OAuth's at the OAuth endpoints, and Problem Details elsewhere, with a `type` of its own for each error the app acts on.
- **Development:** an endpoint of the development environment makes ID tokens for test people. Sign-in then runs the same path with neither Google nor Apple.

The examples carry ID tokens whose claims read as a provider's, signed by nobody. `tools/check.py` checks them against the schema. Four broken examples, tried by hand, failed it.

**Problems / unfinished:** Neither the app nor the cloud implements it yet. Homes, their members and devices, and set-up's registration come in later minor versions.

**Next:** The cloud's side, in ai-cloud's `accounts` module. The app's `account` module, against the development environment first.

## 2026-11-03 — People in a home, from what large projects do

**Done:** [ADR-0009](../decisions/0009-people-in-a-home.md) redone, still proposed. The owner asked that what people experience follow large projects, rather than being decided here. The first draft had reasoned mostly from a few help pages.
- **Read this time:** Tuya's public SDK, Google Home, SmartThings, Apple Home, Home Assistant, Telegram, and the code of Homebox and Mealie.
- **What changed:**
  - a home is deleted only by its last person with an account, as in Google Home and Tuya;
  - handing it over is one step among its people, as in Tuya and Telegram, with no offer to accept;
  - a person's name is the home's, as in Tuya and Home Assistant.
- **What they confirmed:** the role table, which is Tuya's, and a code that works once and can be revoked.
- **Where it departs from them,** the ADR says why: no invitation to a known account, and a fresh sign-in before a home is deleted or handed over.

**Problems / unfinished:** A few claims rest on search excerpts or third-party pages, because the originals refuse automated readers or were not found. The ADR marks them, and the decision does not depend on them.

**Next:** The owner's decision on ADR-0009. The app API 1.1, on it.

## 2026-11-03 — The app API, version 1.1

**Done:** [`protocols/app/`](../../protocols/app/README.md): homes and the people in them, on [ADR-0009](../decisions/0009-people-in-a-home.md), with the schema and a new example.
- **Homes:** a person creates one, with a name, a time zone and languages. Its owner, once its last person with an account, deletes it after a fresh sign-in, which revokes its devices' registrations.
- **People:** one list for people with accounts and profiles, one identifier for a person in a home, and a name that is the home's.
- **Invitations:** a code that works once and is kept as a hash. A link carries it in its fragment, and requests in their body, so that no log sees it.
- **Handing over:** one step, after a fresh sign-in. The old owner becomes an admin.
- **What ai-cloud asked for:** the status of a refused ID token at linking, names with control characters, and the note on what the cloud implements.

The new example validates. A script also tried 15 good bodies, which pass, and 38 broken ones, which fail.

**Decisions:** The owner accepted ADR-0009, after reading a summary of it, and chose to build the whole of version 1.1 in ai-cloud at once, though its architecture would build invitations and several homes when others join.

**Problems / unfinished:**

- A link needs the project's domain, for the phone to open the app.
- No side implements version 1.1 yet.

**Next:** After the merge, tag `app/v1.1`. Then ai-cloud's `accounts`, and ai-app's `homes`.

## 2026-11-03 — The app API 1.1, in the cloud

**Done:** ai-cloud implements version 1.1 ([ai-cloud#20](https://github.com/trungnguyen278/ai-cloud/pull/20)), but for Apple and the page at `/join`, and the app API's README says so. `app/v1.1` is tagged.

**Problems / unfinished:**
- **`/join`** waits for two things: MF2's Python library brought up to the specification ([ADR-0007](../decisions/0007-catalogs.md)), since the page is text that people read, and the project's domain, which App Links and universal links need.
- **Patterns:** JSON Schema reads them as ECMA-262 does, and Python's `re` otherwise, as measured on 2026-11-03.
  - Python's `$` also matches before a last newline, which let `"vi\n"` through every pattern. ai-cloud now reads `$` as ECMA-262 does; ai-robot does not yet.
  - Python's `\d`, `\w` and `\s` take in more characters. Only the email's pattern uses one, `\s`, and the two disagree on six characters there.

  [RFC 9485](https://www.rfc-editor.org/rfc/rfc9485) (I-Regexp) leaves those classes out, so that every engine reads a pattern alike. Whether the protocols keep to it is the owner's to decide.

**Next:** The owner's decision on the patterns. ai-app's `account` and `homes` modules, against the development cloud.

## 2026-11-04 — The app API 1.3: refreshing again after a lost answer

**Done:** [ADR-0011](../decisions/0011-refreshing-again.md), and the app API 1.3, which specifies it.
- **The problem,** met while building ai-app's client: a refresh whose answer is lost on the way ends the session. The cloud has rotated the token, and the app's next refresh presents the old one, which counts as stolen.
- **The rule:** for `refresh_reuse`, 60 seconds, after its first use, a refresh token refreshes again while its replacement is unused, and the replacement then stops working. Any other token presented again still ends its session. Okta and Auth0 allow the same retry.
- **`sign-in.json`** now shows the retry. Its stolen copy comes after the app has refreshed again, so that the example replays without waiting for the window to pass.

**Decisions:** delegated to the assistant, as in the entry before. Okta's longest grace period sets the starting point; ai-cloud's configuration sets its own.

**Problems / unfinished:** No side implements 1.3 yet.

**Next:** After the merge, tag `app/v1.3`. Then ai-cloud implements it, without a new table: a token may refresh again if it is the session's last used one. Then ai-app's `account`, whose session retries a refresh only after no answer came.
